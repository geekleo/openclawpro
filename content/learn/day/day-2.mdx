## 让 AI 真正理解你的意图

昨天我们成功安装了 OpenClaw 并完成了第一次对话。今天，我们将学习如何与 AI 进行更高效的沟通——这是决定你能否真正驾驭 AI 的关键技能。

在进入正题之前，先来看一个真实场景。假设你正在开发一个电商系统，需要 AI 帮你编写一个购物车模块。看看两种不同的提问方式会得到怎样截然不同的结果：

**随意提问**：

```
帮我写一个购物车功能。
```

AI 的输出可能是一段笼统的伪代码，缺少细节，无法直接使用，甚至可能用了你不熟悉的语言或框架。

**精心设计的提问**：

```
你是一位有 8 年经验的 Python 后端工程师，精通 FastAPI 和 SQLAlchemy。
我正在开发一个 B2C 电商平台，后端使用 FastAPI + PostgreSQL，
目前用户认证模块已经完成。
请帮我实现购物车模块，包含以下功能：
1. 添加商品到购物车（支持数量修改）
2. 删除购物车中的商品
3. 查询当前用户的购物车列表（含商品名称、单价、数量、小计）
4. 购物车商品全选/取消全选

请使用 FastAPI 的 Router 结构，包含 Pydantic 模型定义、
SQLAlchemy ORM 模型和完整的 CRUD 接口。每个接口添加中文注释。
```

第二种方式得到的输出是一份可以直接复制到项目中运行的完整模块代码，包含数据模型、接口定义、错误处理，甚至连注释都恰到好处。同样的 AI，同样的模型，结果却天壤之别。

这就是 Prompt 的力量。

### 为什么 Prompt 很重要？

很多人觉得和 AI 对话就是「随便说两句」，但事实上，Prompt（提示词）的质量直接决定了 AI 输出的质量。根据多项研究和实践数据显示：

- 经过优化的 Prompt 可以将 AI 输出的准确率提升 40%-60%
- 在编程任务中，结构化的 Prompt 让生成代码的首次可用率从不到 30% 提升到 80% 以上
- 使用角色设定的 Prompt 在专业领域任务中表现提升显著，尤其是在需要领域知识的场景下

换句话说，学会写 Prompt 不是锦上添花，而是决定你能否高效使用 AI 的核心能力。

让我们再来看几个不同领域的对比：

**编程场景**：

- 普通：「帮我写一个排序算法」
- 优质：「请用 Python 实现一个归并排序函数，输入为整数列表，返回从小到大排列的新列表。要求：不修改原始列表，添加类型提示，时间复杂度 O(n log n)，并附上三个测试用例」

**写作场景**：

- 普通：「帮我写一封邮件」
- 优质：「请帮我写一封发给客户的项目进度汇报邮件。背景：我们是乙方开发团队，项目是企业 CRM 系统，当前处于第二阶段开发中，进度正常，预计下月底交付。语气要专业但不生硬，字数控制在 300 字以内，包含已完成功能列表、下阶段计划和需要客户配合的事项」

**数据分析场景**：

- 普通：「帮我分析这组数据」
- 优质：「我有一份过去 12 个月的电商销售数据（CSV 格式，包含日期、商品类别、销售额、订单数字段）。请帮我完成以下分析：1) 月度销售趋势及环比增长率 2) 各品类销售额占比 3) 找出销售额最高和最低的月份并分析可能原因。请用 pandas 编写分析代码，并用 matplotlib 生成可视化图表」

每一组对比中，优质 Prompt 都包含了明确的背景、具体的需求、清晰的格式要求。这不是在「为难」AI，恰恰相反——你给 AI 的信息越充分，它就越能精准地帮到你。

### CRTE 框架详解

在 OpenClaw 中编写高质量 Prompt，我们推荐使用 CRTE 框架。这四个字母分别代表：Context（上下文）、Role（角色）、Task（任务）、Expectation（期望）。接下来我们逐一拆解。

#### C - Context（上下文）

上下文是告诉 AI 你的背景信息、当前状况和相关限制条件。好的上下文让 AI 不需要猜测，直接进入正确的思考方向。

**示例 1**：
```
上下文：我们公司是一家 50 人规模的 SaaS 创业公司，
目前使用 React + Node.js 技术栈，数据库是 MongoDB，
刚刚从 JavaScript 迁移到 TypeScript，团队成员对 TS 还在适应阶段。
```

**示例 2**：
```
上下文：我是一名大三计算机专业学生，正在准备毕业设计，
课题是"基于机器学习的文本情感分析系统"，
我有 Python 基础但没有机器学习实战经验，导师要求使用 scikit-learn 库。
```

**常见错误**：
- 不提供任何背景，让 AI 完全靠猜测——比如只说「帮我优化代码」，AI 不知道你用什么语言、什么框架、代码的用途是什么
- 提供过多不相关的背景信息，导致 AI 注意力分散——比如讲了公司历史和融资情况，但其实你只是想让 AI 帮你写一个工具函数

#### R - Role（角色）

角色设定让 AI 以特定的专业视角来回答你的问题。不同的角色会带来不同的思考方式、术语使用和输出风格。

**示例 1**：
```
请你扮演一位有 10 年经验的 DevOps 工程师，
精通 Kubernetes、Terraform 和 CI/CD 流水线设计。
```

**示例 2**：
```
请你扮演一位数据分析师，
擅长用 SQL 和 Python 处理业务数据，
善于将复杂的数据分析结果用非技术人员能理解的方式呈现。
```

**常见错误**：
- 设定的角色与任务不匹配——比如让「前端工程师」来设计数据库架构
- 角色设定过于模糊——比如只说「你是一个专家」，没有说明是哪个领域的专家

#### T - Task（任务）

任务是 Prompt 中最核心的部分，描述你到底想让 AI 做什么。任务描述要具体、可执行、有明确的边界。

**示例 1**：
```
请帮我将以下 Python 2 代码迁移到 Python 3，
重点处理 print 语句、字符串编码、除法运算和 dict 方法的兼容性问题。
代码文件共 3 个，请逐个文件进行迁移并说明每处改动的原因。
```

**示例 2**：
```
请对以下 API 接口设计进行安全性审查，
检查是否存在以下风险：SQL 注入、XSS 攻击、未授权访问、
敏感数据泄露、缺少速率限制。
对于每个发现的问题，请给出风险等级（高/中/低）和修复建议。
```

**常见错误**：
- 任务描述太笼统——「帮我改一下代码」比「帮我把这个函数从同步改为异步，使用 async/await 语法」差很多
- 一次塞入太多不相关的任务——与其一次让 AI 做十件事，不如分成几轮对话逐个完成

#### E - Expectation（期望）

期望是告诉 AI 你想要什么样的输出格式和质量标准。这一步经常被忽略，但它直接决定了 AI 输出的「可用性」。

**示例 1**：
```
请以 Markdown 表格的形式输出对比结果，
列包含：方案名称、优点、缺点、适用场景、学习曲线。
表格下方附上你的推荐方案及理由，控制在 200 字以内。
```

**示例 2**：
```
请用 JSON 格式返回结果，包含以下字段：
- summary：一句话总结（不超过 50 字）
- issues：问题列表，每个问题包含 type、severity、description、suggestion
- score：代码质量评分（1-10）
```

**常见错误**：
- 对输出格式没有任何要求，导致 AI 随意组织内容，可能得到大段文字而你需要的是一个列表
- 期望不切实际——比如要求 AI「给出 100% 正确的答案」或「考虑所有可能的边界情况」

**完整 CRTE 示例**：

```
你是一位资深的 Python 开发工程师（Role），
我正在开发一个电商后台系统，使用 Django + PostgreSQL（Context），
请帮我设计用户权限管理模块的数据库表结构（Task），
请用 Django Model 代码输出，添加中文注释说明每个字段的用途，
并附上一个权限检查的中间件示例（Expectation）。
```

### Prompt 反模式

了解了好的 Prompt 怎么写，我们还需要知道哪些写法要避免。以下是最常见的五种反模式：

#### 1. 过于模糊

```
帮我搞一下那个功能。
```

问题：AI 完全不知道「那个功能」是什么，「搞一下」是新增、修改还是删除。这种 Prompt 几乎不可能得到有用的回答。

**改正**：明确说出你要做什么、针对什么、达到什么效果。

#### 2. 信息过载

```
我们公司成立于 2018 年，主要做 B2B SaaS 产品，
目前有 200 多个客户分布在制造业和零售业，
去年营收增长了 150%，团队从 20 人扩展到了 80 人，
技术栈经历了从 PHP 到 Java 再到 Go 的演变......
（以上写了 500 字后）
请帮我写一个配置文件的解析函数。
```

问题：前面的大量信息对「写一个配置文件解析函数」这个任务没有任何帮助。过多无关信息反而会干扰 AI 的判断，导致输出质量下降。

**改正**：只提供与当前任务直接相关的信息。

#### 3. 自相矛盾

```
请用简洁的语言详细解释每一个细节，
输出尽量简短但要面面俱到，
用初学者能懂的方式讲解高级技术原理。
```

问题：「简洁」和「详细解释每一个细节」矛盾；「尽量简短」和「面面俱到」矛盾。AI 会在两个方向上反复纠结，最终输出一个折中但两头不讨好的结果。

**改正**：先想清楚你最核心的需求是什么，然后一致地表达。

#### 4. 缺少关键上下文

```
这段代码为什么报错了？
```

问题：没有附上代码内容，没有说明错误信息，没有提供运行环境。AI 只能给出泛泛的排查建议，无法定位具体问题。

**改正**：至少提供代码片段、完整的错误信息、运行环境和你已经尝试过的解决方案。

#### 5. 角色错配

```
你是一位资深的 UI 设计师。
请帮我编写一个高并发的消息队列系统，
支持百万级 QPS，使用 Kafka 集群部署。
```

问题：UI 设计师的角色与后端分布式系统开发任务完全不匹配。虽然 AI 仍然会尝试回答，但角色设定会影响它的思考框架和术语使用，导致输出质量打折扣。

**改正**：选择与任务领域匹配的角色，或者不设定角色也比设定错误的角色更好。

### Workspace 配置

OpenClaw 的 Workspace 功能让你可以为不同的项目创建独立的工作空间，每个空间可以有自己的配置、Prompt 模板和上下文记忆。Workspace 是 OpenClaw 中最实用的功能之一——一旦配置好，你就再也不需要重复地告诉 AI 你的项目背景了。

#### 创建工作空间

```bash
# 创建一个名为 my-project 的工作空间
openclaw workspace create my-project

# 切换到该工作空间
openclaw workspace use my-project

# 查看当前工作空间
openclaw workspace current

# 列出所有工作空间
openclaw workspace list
```

#### 工作空间目录结构

创建工作空间后，OpenClaw 会在你的项目目录下生成以下结构：

```
.openclaw/
├── config.yaml          # 核心配置文件
├── system_prompt.md     # System Prompt（可选，支持 Markdown 格式）
├── templates/           # 自定义 Prompt 模板目录
│   ├── code-review.md
│   └── bug-analysis.md
├── context/             # 上下文文件目录
│   ├── architecture.md
│   └── coding-style.md
└── history/             # 对话历史记录（自动生成）
```

每个目录和文件都有明确的职责分工，让你的工作空间保持整洁有序。

#### config.yaml 完整配置参考

```yaml
workspace:
  # 基础信息
  name: my-project                    # 工作空间名称
  description: "电商后台管理系统"      # 工作空间描述（可选）

  # 模型配置
  model: gpt-4                        # 默认使用的模型
  fallback_model: gpt-3.5-turbo       # 主模型不可用时的备选模型
  temperature: 0.7                    # 创造性程度 0-1，越高越有创意
  max_tokens: 4096                    # 单次回答的最大 token 数

  # System Prompt —— 每次对话自动加载的角色设定
  system_prompt: |
    你是一位全栈开发助手，精通 React 和 Node.js。
    项目使用 TypeScript，请始终遵循项目的代码风格。
    回答问题时优先考虑代码的可维护性和可测试性。

  # 上下文文件 —— 让 AI 了解你的项目
  context_files:
    - ./README.md                     # 项目说明
    - ./docs/architecture.md          # 架构文档
    - ./docs/api-spec.md              # API 规范
    - ./.eslintrc.js                  # 代码规范配置

  # 输出偏好
  output:
    language: zh-CN                   # 回答使用的语言
    code_style: google                # 代码风格标准
    include_comments: true            # 代码是否包含注释
```

#### context_files 的使用策略

`context_files` 是 Workspace 中非常强大的功能。它让 AI 在每次对话开始时自动读取指定的文件内容，从而了解你的项目背景。以下是几条使用建议：

**应该加入的文件**：
- 项目 README 或架构文档——让 AI 了解项目整体情况
- 代码规范配置（如 .eslintrc、.prettierrc）——让生成的代码自动遵循你的规范
- API 接口文档——让 AI 在编写相关代码时参考正确的接口定义
- 数据库 Schema 文件——让 AI 了解数据结构

**不应该加入的文件**：
- 包含敏感信息的文件（如 .env、密钥文件）
- 超大的文件（如打包后的 bundle 文件、大型数据集）
- 频繁变动的日志文件

#### 模型选择策略

OpenClaw 支持多种模型，不同场景适合不同的选择：

| 场景 | 推荐模型 | 原因 |
|------|---------|------|
| 复杂代码架构设计 | gpt-4 | 需要强大的推理和规划能力 |
| 日常代码编写 | gpt-3.5-turbo | 速度快，性价比高，满足大部分需求 |
| 代码审查和 Bug 分析 | gpt-4 | 需要深度理解代码逻辑 |
| 文档和注释编写 | gpt-3.5-turbo | 文本生成任务不需要最强的推理能力 |
| 技术方案评审 | gpt-4 | 需要综合考虑多个维度 |

你可以在 config.yaml 中设置默认模型，也可以在对话时随时切换：

```bash
# 临时切换模型
openclaw chat --model gpt-4
```

### 多 Workspace 管理

当你同时参与多个项目时，多 Workspace 管理就变得至关重要了。

#### 工作空间切换

```bash
# 查看所有工作空间
openclaw workspace list

# 输出示例：
#   my-ecommerce     (当前)
#   data-pipeline
#   mobile-app
#   personal-blog

# 切换到另一个工作空间
openclaw workspace use data-pipeline

# 快速在两个工作空间间切换（类似 git checkout -）
openclaw workspace switch
```

切换工作空间后，system_prompt、context_files、模型配置都会自动变更，你不需要手动调整任何设置。

#### 工作空间模板

如果你的团队有多个类似的项目，可以创建工作空间模板来快速初始化：

```bash
# 基于当前工作空间创建模板
openclaw workspace template save react-fullstack

# 用模板创建新工作空间
openclaw workspace create new-project --template react-fullstack
```

模板会保存 config.yaml 的所有配置和 templates 目录中的 Prompt 模板，但不会包含对话历史和上下文文件的实际内容。

#### 团队共享配置

将 `.openclaw/` 目录提交到 Git 仓库中（注意排除 history 目录），团队成员 clone 项目后就能自动获得统一的工作空间配置：

```bash
# .gitignore 中的推荐配置
.openclaw/history/
.openclaw/*.local.yaml
```

在 `.openclaw/config.yaml` 中写入团队统一的配置，成员可以在 `config.local.yaml` 中覆盖个人偏好（如模型选择），而不会影响团队配置。

### System Prompt 进阶

System Prompt 是每次对话的「隐形指令」，它在对话开始前就告诉 AI 应该以什么方式工作。写好 System Prompt 可以大幅减少你每次对话时需要重复说明的内容。

#### 编写高效 System Prompt

一个优秀的 System Prompt 应该包含以下要素：

```markdown
# 角色定义
你是一位高级全栈工程师，专注于 React + Node.js + PostgreSQL 技术栈。

# 项目背景
当前项目是一个在线教育平台，已有用户量约 5 万人，
正在进行从单体架构到微服务的重构。

# 行为准则
- 编写代码时始终使用 TypeScript
- 遵循项目既有的代码规范（参考 context_files 中的 .eslintrc）
- 所有函数必须添加 JSDoc 注释
- 优先考虑代码的可测试性，每个公开函数都应该容易编写单元测试
- 涉及数据库操作时使用参数化查询，防止 SQL 注入

# 回答风格
- 先给出解决方案的整体思路，再展示具体代码
- 如果有多种方案，列出各方案的优劣对比
- 对于可能产生破坏性影响的操作，务必在代码前给出警告
```

#### 条件指令

你可以在 System Prompt 中加入条件判断逻辑，让 AI 根据不同情况采取不同策略：

```markdown
# 条件指令

当用户提供的代码片段少于 20 行时：
  直接给出完整的修改后代码。

当用户提供的代码片段超过 20 行时：
  只给出需要修改的部分，用注释标注修改位置。

当用户的问题涉及数据库结构变更时：
  除了给出 SQL 语句外，还需要提供回滚方案。

当用户没有指定编程语言时：
  默认使用 TypeScript。
```

#### 输出格式控制

通过 System Prompt 统一 AI 的输出格式，让每次对话的结果都保持一致：

```markdown
# 输出格式要求

代码回答格式：
1. 先用一句话概述解决思路
2. 给出完整代码（带注释）
3. 列出代码的依赖项（如果有新依赖）
4. 提供简要的使用说明

Bug 分析格式：
1. 问题原因（一句话）
2. 根因分析（详细解释）
3. 修复代码
4. 如何避免类似问题的建议

技术方案格式：
1. 方案概述
2. 架构图（用 ASCII 或 Mermaid 语法）
3. 技术选型及理由
4. 实施步骤
5. 风险点和应对策略
```

### 实用 Prompt 模板库

以下是一组在日常工作中经过验证的高效 Prompt 模板。你可以直接使用，也可以根据自己的需要进行调整。

**代码审查模板**：
```
请审查以下代码，从以下维度进行评估：
1. 潜在的 Bug 和逻辑错误
2. 性能瓶颈（时间复杂度和空间复杂度）
3. 安全漏洞（注入攻击、权限绕过等）
4. 代码可读性和命名规范
5. 是否符合 SOLID 原则

对每个发现的问题，请给出：问题描述、严重等级（高/中/低）、
修改建议和修改后的代码片段。
```

**技术方案设计模板**：
```
请针对以下需求提供技术方案：[需求描述]

方案内容需包含：
1. 整体架构设计（附文字描述的架构图）
2. 核心模块拆分和职责说明
3. 技术选型及选择理由（至少对比 2 个备选方案）
4. 核心流程的时序描述
5. 数据库表结构设计（如涉及）
6. 接口定义（RESTful 风格）
7. 风险评估和应对策略
8. 预估工时（按模块拆分）
```

**Bug 分析模板**：
```
我遇到了以下 Bug，请帮我分析和修复：

错误信息：[粘贴完整的错误日志]
相关代码：[粘贴相关代码]
复现步骤：[描述操作步骤]
环境信息：[操作系统/运行时版本/相关依赖版本]

请提供：
1. 错误原因分析
2. 修复方案（给出修改后的代码）
3. 如何验证修复是否成功
4. 防止类似问题再次发生的建议
```

**文档编写模板**：
```
请为以下代码/模块编写技术文档：

文档结构要求：
1. 模块概述（功能简介和设计目标）
2. 快速开始（最简使用示例）
3. API 参考（每个公开方法的签名、参数说明、返回值、异常情况）
4. 配置项说明
5. 常见问题（FAQ）

风格要求：语言简洁清晰，示例代码可直接运行，
面向有一定开发经验但不熟悉本模块的开发者。
```

**数据分析模板**：
```
请分析以下数据集：[数据描述或文件路径]

分析目标：
1. 数据概览（字段说明、数据量、缺失值情况）
2. 描述性统计（均值、中位数、标准差、分布特征）
3. 关键指标趋势分析
4. 异常值检测和可能的原因
5. 可视化图表（使用 matplotlib/seaborn）
6. 结论和业务建议

请用 Python pandas 编写分析代码，代码中添加中文注释。
```

**邮件起草模板**：
```
请帮我起草一封邮件：

发件人角色：[你的职位]
收件人：[收件人及其角色]
邮件目的：[简述目的]
背景信息：[相关背景]

要求：
- 语气：[正式/半正式/友好]
- 字数：[控制范围]
- 结构：开头致意 -> 正文内容 -> 行动项 -> 结尾
- 如果涉及敏感内容，请用委婉的表达方式
```

**会议纪要模板**：
```
请根据以下会议信息整理会议纪要：

会议主题：[主题]
参会人员：[人员列表]
会议内容：[你的笔记或录音转文字]

纪要格式：
1. 会议基本信息（时间、地点、参会人）
2. 议题和讨论要点（按议题分段）
3. 关键决策（明确列出）
4. 行动项（负责人 + 截止日期）
5. 遗留问题（需后续跟进的事项）

语言简练，重点突出决策和行动项。
```

**学习辅助模板**：
```
我正在学习 [技术/概念名称]，当前水平是 [初学者/中级/高级]。

请帮我：
1. 用通俗的类比解释核心概念
2. 给出由浅入深的学习路径（分 3-5 个阶段）
3. 每个阶段推荐 1-2 个动手练习
4. 列出常见的理解误区和正确理解方式
5. 推荐高质量的学习资源（优先中文资源）

解释时避免直接堆砌术语，先建立直觉再引入专业定义。
```

### 动手练习

学完今天的内容，是时候实际操作一下了。以下三个练习帮你巩固所学的 Prompt 技巧和 Workspace 配置方法。

#### 练习一：改写 Prompt

下面有一个低质量的 Prompt，请用 CRTE 框架将它改写为高质量版本：

```
帮我写个登录页面。
```

参考改写方向：指定前端框架、页面包含的具体元素（用户名/密码/验证码/记住我/第三方登录）、UI 风格、是否需要表单验证、是否需要响应式适配等。

试着把改写后的 Prompt 发送给 OpenClaw，对比两种 Prompt 得到的输出差异。

#### 练习二：配置你的第一个 Workspace

为你当前正在开发的项目（或一个你感兴趣的学习方向）创建一个 Workspace：

```bash
# 第一步：创建工作空间
openclaw workspace create my-first-workspace

# 第二步：编辑配置文件
# 打开 .openclaw/config.yaml，设置好 model、system_prompt 和 context_files

# 第三步：验证配置
openclaw workspace info
```

配置完成后，开始一个对话来测试你的 system_prompt 是否生效。一个简单的验证方法：在 system_prompt 中要求「所有代码使用中文注释」，然后让 AI 生成一段代码，看注释是否是中文的。

#### 练习三：模板实战

从上面的模板库中选择一个你最常用的场景（例如代码审查），用它来分析你自己项目中的一段真实代码。注意观察：

1. 使用模板前后，AI 输出的结构化程度有什么变化？
2. 模板中的哪些字段对输出质量影响最大？
3. 你觉得这个模板还有哪些可以优化的地方？

把你的优化版本保存到 `.openclaw/templates/` 目录中，形成你自己的模板库。

### 今日小结

今天你学到了高效 Prompt 编写的核心方法和 Workspace 配置技巧。让我们回顾一下关键要点：

1. **Prompt 质量决定输出质量**——同样的 AI 模型，精心设计的 Prompt 和随意编写的 Prompt 得到的结果可能天差地别
2. **CRTE 框架**——Context（上下文）、Role（角色）、Task（任务）、Expectation（期望），四个要素缺一不可
3. **避免反模式**——警惕过于模糊、信息过载、自相矛盾、缺少上下文、角色错配这五种常见错误
4. **Workspace 是效率倍增器**——一次配置，永久生效，告别重复的背景说明
5. **System Prompt 是隐形指令**——用好条件指令和格式控制，让 AI 的输出始终符合你的标准
6. **模板库是你的武器库**——积累优质模板，让每次提问都站在更高的起点上

记住：Prompt 工程不是一次性的工作，而是一个持续优化的过程。从今天开始，留意每次和 AI 对话的效果，不断迭代你的 Prompt 和 Workspace 配置。
